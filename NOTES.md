# Engineering notes

Log surprises, failed attempts, and decisions here while working.

## Toolchain

- Development environment: Windows with Ubuntu on WSL 2 and Docker Desktop.
- Trivy 0.76.2 and Grype 0.121.2.

## `set -e` does not protect command substitution

The first version of `scripts/pin-images.sh` pulled images inside a function
called from `$(...)`. Bash ignores `set -e` there, so a failed `docker pull` did
not stop the script. The next command then reported `No such image`, which hid
the real failure.

Fix: pull images before any command substitution, so a failed pull stops the
script straight away. I tested this with a simulated pull failure, and the script
exited without changing `versions.env`.

## nginx's packaging tries to download a tool from a dead URL

Building the `.deb` through nginx's own packaging (`pkg-oss`) failed at the
source-tree assembly step:

    curl: (22) The requested URL returned error: 404
    xslscript-01dc9ba12e1b.tar.gz: FAILED

`pkg-oss` generates the Debian changelog from XML, and that step first downloads
a helper tool (`xslscript`) to compile the XSLT. The download URL is no longer
hosted, so the build aborted. Nothing to do with our patch or nginx itself.

Fix: we set our own package version and changelog entry anyway (`dch`), so the
generated changelog is not needed. The changelog rule is not phony, so writing a
minimal valid `debian/nginx.deb-changelog` before running the build satisfies the
rule and skips the broken download. See `build/build.sh` step 5.

Takeaway: pinning the upstream packaging to a fixed revision makes the build
reproducible, but it does not protect against an external URL that rots. A fully
hermetic build would vendor that helper too.

## Dynamic modules: from copied binaries to from-source packages

The upstream image ships four dynamic modules (geoip, image-filter, njs, xslt).

**First attempt (superseded).** Rather than build them, we copied the prebuilt
`.so` files out of the upstream image. nginx builds modules with `--with-compat`,
so a stock module loads into any same-version nginx; it worked once we also
installed the libraries the `.so` files link (libxml2, libxslt, libgd, libgeoip),
which upstream gets via its module packages.

**Why that was wrong.** An audit against the brief flagged it: those are
repackaged upstream binaries, not compiled output ("no pre-baked binaries"). And
because they bypassed dpkg, the scanners could not see them at all -- any njs CVE
would simply never be reported.

**Now.** `build.sh` builds all four as real packages with pkg-oss's module rules
(`rules-module-<name>`), from the same patched nginx source, stamped `+echo1`.
They depend on the virtual package `nginx-r1.25.5`, which our nginx package
provides, so they install cleanly next to it, and apt pulls their runtime
libraries from their own dependencies -- the hand-maintained library list is gone.
Two snags on the way:

1. Each module's changelog is generated by the same dead xslscript helper as
   nginx's, so `build.sh` pre-seeds one per module.
2. pkg-oss fetches njs from nginx's contrib mirror (verified with its pinned
   SHA-512) and falls back to `hg.nginx.org`, which is retired. If the mirror is
   down, `build.sh` uses njs's official GitHub release tarball, checked against a
   SHA-512 pinned in `versions.env`.

The Containerfile gate fails the build unless all four modules are our `+echo1`
packages, and the test fixture loads all six module objects in both images.

## The backport compiled but was not in the binary

The compatibility suite's CVE test caught this: the drop-in image returned 200
on the alias+rewrite trigger, exactly like the unpatched upstream, instead of the
patched build's 500. The parity tests all passed, so the image was a faithful
drop-in -- of the *unpatched* nginx.

Cause: the build added the patch to `debian/patches/series` and trusted
`dpkg-buildpackage` (source format "3.0 (quilt)") to apply the series at build
time. In this setup that application did not happen, so nginx compiled from the
pristine source.

Fix: apply the patch directly to the source tree that `debian/rules` compiles
(it copies `$(CURDIR)/src` into the build dir), then verify with a reverse
dry-run that it is really applied before building. The behavioural CVE test now
passes.

Lesson: "the patch applies cleanly" is not "the patch is in the binary." Only a
test that exercises the fixed behaviour proves the backport shipped.

## VEX on a locally-built image: which identifier does Grype match?

The backport CVE needed a VEX statement, which was straightforward to write but
fiddly to make Grype actually honour. Grype applies a statement when the
statement's *product* matches the scanned image and its *subcomponent* matches
the vulnerable package. The subcomponent was easy -- copy the package PURL
verbatim from Grype's own report. The product was the catch: a locally built
image was never pushed to a registry, so there is no canonical reference for it.
Grype knows it variously by tag, image ID and manifest digest depending on how
it was invoked.

Rather than hard-code one guess, `tools/make_vex.py` reads all of them out of the
candidate report and emits one statement listing all three as products, so the
assertion matches whichever identifier Grype uses. `make vex` then regenerates
the document and re-scans with `--vex --show-suppressed`, asserting the CVE moved
to the suppressed list -- the VEX is self-verifying rather than taken on faith.

Lesson: a VEX document is only useful if the consuming scanner matches it, and
PURL/product matching on locally-built images is the part that bites. Deriving
the identifiers from the scan output instead of hand-writing them removes the
guesswork.

## The scan diff counted missing packages as fixes

The first image left out `curl` and `ca-certificates`, and so also the `openssl`
CLI and curl's krb5/ldap/ssh2/nghttp2 libraries. The diff tool counted every
finding that disappeared as "removed by the rebuild", and the README repeated it:
489 removed, "nothing here is removed". About 214 of those were just curl's CVEs
leaving with curl. The tell: 38 of curl's CVEs have *no fixed version* in Debian,
so no update could ever have removed them.

That was both a drop-in regression (a `curl` healthcheck or an HTTPS `proxy_pass`
checking the system CA bundle would break) and a false claim. With the packages
restored, the honest numbers are 846 -> 465 (381 fixed). `scan.sh` now records
each image's full package list, and `diff_scans.py` splits every disappeared
finding into "fixed (still shipped, newer version)" and "package not shipped".
`make scan-candidate` fails if any upstream package is missing, so the claim is
enforced rather than asserted.

Lesson: a number that only goes down is not evidence. Ask *why* each finding left.

## The build filled the Windows drive and corrupted WSL

The build compiles nginx twice (the normal binary and `nginx-debug`, both shipped
in upstream's package) plus eight module-only builds (each of the four modules in
a normal and a `-debug.so` variant), with njs also building the QuickJS engine and
its CLI -- and every build tree stayed baked into the throwaway build image. On WSL,
Docker's virtual disk and the distro's live on the Windows drive and only grow.
The drive hit 0 bytes free mid-scan; Ubuntu crashed, then failed to start with
I/O errors (`getpwnam ... failed 5`) until WSL was restarted.

Fixes: `build.sh` and `build-pcre2.sh` delete their work trees in the same layer,
the scripts remove the throwaway build images after copying the `.deb`s out, and
`make doctor` (run first by `make all`) fails below 10 GB free -- checking the
Windows drive specifically under WSL. The scans can also be pinned to the existing
DB (`GRYPE_DB_AUTO_UPDATE=false TRIVY_SKIP_DB_UPDATE=true`) so a near-full disk
doesn't trigger a database download, and so the comparison stays fair.

## The upstream njs module came from a later packaging revision

The upstream image's env shows `NJS_RELEASE=3~bookworm`: its njs module package is
`1.25.5+0.8.4-3~bookworm`, while the pkg-oss `1.25.5-1` tag we first pinned builds
release 1. Releases 2 and 3 (pkg-oss `62030fe`, `e23535b`, `14d7f18`) only change
how the `njs` command-line tool is built (libatomic, explicit `--with-quickjs`);
the nginx module itself is built the same way, so this was not a security gap.

Still, the README claimed we built from "the exact revision that built the
original image", and for njs that was not true. We now pin pkg-oss `14d7f18` --
still nginx 1.25.5-1, njs release 3 -- after checking that nothing else in between
affects a Debian bookworm build (identical checksums; the only rules change is
Ubuntu-24-only). `build.sh` fetches that commit directly and reads each module's
release number from pkg-oss instead of assuming 1.

The same check also found the `nginx` passwd entry differed (no comment,
`/usr/sbin/nologin` instead of `/bin/false`); it now matches upstream exactly.

## Tests that could not fail

Asking "could this test pass while the image is broken?" of every test found
several that could:

- **Parity without anchors.** The parity tests compared the two images to each
  other but never checked either was right; two images broken the same way (a
  failed mount, a dropped connection) would "match". The raw-socket tests were
  the worst: two servers that both close the connection match on empty bytes.
  Every scenario now states what nginx must return, checked against upstream
  before comparing.
- **A gzip path that never worked.** The test "decoded" gzip bodies, but
  `requests` already decodes them, so the extra decode always failed -- and an
  `except OSError: pass` swallowed it every time. Worse, `requests` asks for gzip
  on *every* request by default, so every scenario on `big.txt` was silently
  gzipped and the plain path was never tested. Removing the silent `except` made
  seven tests fail at once, which is how this surfaced. Requests now ask for
  `identity` unless a scenario negotiates gzip, and the gzip scenario proves the
  response really was gzipped and decodes to the file.
- **image-filter** only checked for a PNG, not that it was resized; it now checks
  the 8x8 dimensions in the PNG header.

`make selfcheck` closes the loop: it runs the suite against upstream itself
(only the CVE test may fail) and against nginx 1.27 (the parity suites must
fail), proving the suite fails when it should.

Lesson: a green suite proves nothing until you have seen it go red for the right reason.
