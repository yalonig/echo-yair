# echo-nginx — a patched, drop-in rebuild of `nginx:1.25-bookworm`

A from-source rebuild of the official `nginx:1.25-bookworm` image that removes
known vulnerabilities using two different remediation techniques, while staying a
true drop-in replacement. The whole project reproduces from a clean checkout with
one command.

```bash
make all      # build the .deb, build the image, run the compat tests, rescan + diff
```

- **nginx** is compiled from upstream source (1.25.5), not repackaged from apt.
- **CVE-2026-15176** (a buffer overflow in nginx itself) is fixed by **backporting**
  the upstream patch — the package version can't change, so this one needs a VEX
  statement for scanners to see it.
- **PCRE2 and OpenSSL** are fixed by a **version bump** — rebuilding on current
  Debian bookworm moves them to patched versions, which scanners detect on their own.
- The image boots through the original entrypoint, keeps the same user, ports,
  and all four dynamic modules, and passes an automated response-parity suite
  against the original.

---

## Prerequisites

Linux (or WSL2 on Windows) with: `docker`, `make`, `python3`, `git`, and the two
scanners `trivy` and `grype`. Check everything is present:

```bash
make doctor
```

## Quick start

```bash
make pin            # resolve the base/upstream image tags to fixed digests (once)
make all            # deb -> image -> test -> rescan+diff
```

Individual stages:

| Command | What it does |
|---|---|
| `make pcre2` | Rebuild the version-bumped PCRE2 `.deb` from Debian source. |
| `make deb` | Compile the patched nginx `.deb` from source in a clean `debian:bookworm-slim`. |
| `make image` | Build the drop-in image `echo-nginx:1.25.5` from the `.deb`. |
| `make test` | Boot both images and assert identical responses + prove the CVE fix. |
| `make scan-baseline` | Scan the original image (committed as the baseline). |
| `make scan-candidate` | Scan the rebuilt image and diff it against the baseline. |

Build outputs (`.deb`, images, raw scan JSON) are intentionally **not** committed —
they are regenerated by `make`. The readable scan reports and the diff are committed
as evidence under `scans/`.

## The two remediation techniques

The brief asks for at least two *different* techniques. Removing components does
not count — and nothing here is removed; the four dynamic modules the original
ships are all preserved (see below).

### 1. Backport — CVE-2026-15176 (nginx)

A buffer overflow in `ngx_http_map_uri_to_path()`: in a `location` that uses
`alias` together with `rewrite`, the rewritten URI can become shorter than the
location prefix, and nginx writes past the end of the path buffer. Unauthenticated.

- **Why backport:** the fix first shipped in nginx 1.31.7 / 1.30.6, but we ship a
  1.25.x package to stay a drop-in. So we take the upstream one-line fix
  ([`f8a23425`](https://github.com/nginx/nginx/commit/f8a23425bd6840c4c36b4264edf576ba3646156f))
  and apply it to 1.25.5. The patch, with DEP-3 provenance, is in
  `build/patches/CVE-2026-15176.patch`.
- **The version does not change** (`1.25.5`), so Trivy/Grype keep reporting it even
  though the code is fixed. That is the case VEX exists for (see *Scanning*).
- **Proof:** `test/compat_test.py::test_cve_2026_15176_is_fixed` sends the exact
  trigger request to both images. The patched build refuses the path mapping — it
  logs `"alias" cannot be used in location "/foo/" where URI was rewritten` and
  returns an empty body — while the original maps the path and returns it.

### 2. Version bump — PCRE2 (from source) and OpenSSL

nginx links PCRE2 (every config regex) and OpenSSL (TLS), both of which have CVE
fixes in Debian bookworm:

| Library | Original | Rebuilt | Effect |
|---|---|---|---|
| `libpcre2-8-0` | `10.42-1` | `10.42-1+deb12u2+echo1` | clears 7 CVEs (incl. an arbitrary-code-execution OOB write) |
| `libssl3` | `3.0.11-1~deb12u2` | `3.0.22-1~deb12u2` | clears the OpenSSL set |

- **PCRE2 is rebuilt from source** as the deliberate bump: `build/build-pcre2.sh`
  (run via `make pcre2`) enables Debian source repos, runs `apt source pcre2`,
  bumps the version with a `+echo1` suffix, and `dpkg-buildpackage` produces our
  own `libpcre2-8-0` `.deb`. The image installs that package; nginx links it
  dynamically, so no nginx build flags change. This is the version bump applied as
  a from-source build step, alongside the backport.
- **OpenSSL** is bumped by rebuilding on the current base (`3.0.11` → `3.0.22`).

Because the package versions change, the scanners drop these on their own — no VEX
needed. A safety gate in the `Containerfile` additionally **fails the build** if
either linked library is below its CVE-fixed version
(`dpkg --compare-versions`), so a stale base or a missing PCRE2 package can't
silently ship the vulnerable `10.42-1`.

## Results

Scanned with Trivy 0.76.2 and Grype 0.121.2 (same DB versions for both images, so
the diff is fair). Full reports in `scans/`; the diff is `scans/candidate/diff.md`.

| | Baseline (original) | Candidate (rebuilt) |
|---|---|---|
| Total findings | 846 | 357 |
| Critical | 56 | 9 |
| High | 290 | 89 |

**489 findings removed** (47 Critical, 201 High). Being honest about *why*:

- **The PCRE2 bump shows up in the diff** — its 7 CVEs are in the removed set,
  because the version changed and the scanner can see it.
- **The backport does *not* show up as removed, and that's the whole point of it.**
  The scanner still reports CVE-2026-15176 (the package version is unchanged), so
  it sits in the 357 *remaining* until a VEX statement tells the scanner it's
  fixed. The code is fixed regardless, and the compat test proves it.
- **The large majority of the 489 came for free from rebuilding on a current base**
  — the biggest groups removed are `curl` (104), `openssl` (97), `krb5` (52),
  `expat` (33), `gnutls28` (21), `libxml2` (21). That is a real and valuable effect
  (rebuilding regularly *is* a patching strategy), but it is not hand-crafted
  remediation, so it's reported separately rather than claimed as such.

`remove` is not used as a fix method — no components were removed. The eight CVEs
above are the deliberately targeted ones (one backport, the PCRE2 bump). The
Containerfile's version gate also enforces the OpenSSL bump, which clears the
OpenSSL set (~97 findings); those plus the rest of the ~480 cleared by the base
rebuild are listed in full in [`scans/candidate/diff.md`](scans/candidate/diff.md)
rather than enumerated here.

### Residual risk

**357 findings remain, including 9 Critical and 89 High.** This image is more
secure than the original but is **not** "clean", and should not be presented as
such. Most of what remains has no fixed version available in bookworm yet
(e.g. the `zlib1g` heap-overflow CVE is marked *will-not-fix*), so no amount of
rebuilding or bumping removes it today.

The honest long-term fix is **not** to keep patching 1.25.x: nginx 1.25 is an old
mainline branch, and the `alias`/`rewrite` class of bugs keeps appearing in it. A
production path would move to a currently-supported nginx release on a minimal
(e.g. distroless or Alpine) base and rebuild on a schedule.

## How it's built

### From source, not apt

`build/build.sh` runs inside a clean `debian:bookworm-slim` and, in order:

1. downloads `nginx-1.25.5.tar.gz` and verifies it against the SHA-512 nginx
   publishes;
2. clones nginx's own packaging (`pkg-oss`) pinned to the `1.25.5-1` tag — the
   exact revision that built the original image, so the configure flags match
   (building against today's `pkg-oss` would add modules the original lacks);
3. applies the backport patch directly to the source tree and verifies it;
4. stamps the build version `1.25.5-1~bookworm+echo1`;
5. compiles the `.deb` with `dpkg-buildpackage`.

**`nginx -V` of the rebuilt binary has identical configure arguments to the
original** — same modules, paths, user, and `--with-compat`. The only `-V`
differences are the build-directory string and the (newer) OpenSSL version.

### Drop-in image

`Containerfile` installs the `.deb` onto a clean `debian:bookworm-slim` and
reproduces the original image exactly:

- the `nginx` user (uid/gid 101), `EXPOSE 80`, `STOPSIGNAL SIGQUIT`, entrypoint
  and cmd;
- the upstream `/docker-entrypoint.sh` and `/docker-entrypoint.d/` scripts, reused
  verbatim via a multi-stage copy;
- log forwarding to the container's stdout/stderr;
- **all four dynamic modules** (geoip, image-filter, njs, xslt), copied from the
  original image (ABI-compatible via `--with-compat`) with their runtime libraries
  installed. Verified: `nginx -t` loads all four.

Two intentional differences from the original: the package version carries a
`+echo1` suffix (so the rebuild is traceable), and the image is **261 MB vs
276 MB** — the smaller size is from `--no-install-recommends` and a cleaner layer
set, not from dropping anything.

## Compatibility test

`make test` (pytest, `test/`) boots both images with the same mounted config and
content, then asserts the candidate responds identically to the original across 15
scenarios — static files, 404, HEAD, byte ranges, conditional requests, gzip,
redirect, method-not-allowed, request-too-large, and malformed requests sent over
raw sockets (which a normal HTTP client would "fix" before sending). The only
header ignored is `Date`; gzip bodies are compared decoded.

A 16th test proves the backport changed behaviour, as described above. Scenarios
are data (`test/scenarios.yaml`), so adding a case is a one-line edit.

## Scanning and VEX

The two scanners disagree, which is itself worth noting: **Trivy does not report
CVE-2026-15176 at all; Grype does.** For a backport, where the version can't change,
a scanner that matches on version alone can't tell the code is fixed — so Grype
keeps flagging it on the rebuilt image.

The correct way to resolve that is a **VEX** (Vulnerability Exploitability
eXchange) document: a signed statement that CVE-2026-15176 is `fixed` in this
build, which a scanner consumes (`grype --vex`) to drop the finding. The product
identifier must match the rebuilt package's PURL
(`pkg:deb/debian/nginx@1.25.5-1~bookworm+echo1`). This is the one bonus item not
implemented here; VEX matching against locally-built images is notoriously
finicky, and it was out of scope for the time spent.

## Repo layout

```text
build/
  Dockerfile              # clean debian:bookworm-slim that runs build.sh
  build.sh                # fetch + verify nginx source, apply patches, compile the .deb
  build-pcre2.sh          # version bump: apt source pcre2 -> dpkg-buildpackage
  Dockerfile.pcre2        # clean base that runs build-pcre2.sh
  patches/
    CVE-2026-15176.patch  # the backport, with DEP-3 provenance
Containerfile             # the drop-in image, with the version-bump gate
scripts/                  # doctor, pin-images, scan, build-deb, build-image, run-tests
tools/
  triage.py               # merge Trivy + Grype reports into one CVE table
  diff_scans.py           # baseline-vs-candidate diff
test/                     # pytest compat suite, scenarios, fixtures
scans/                    # committed baseline + candidate reports and the diff
versions.env              # every pinned input (digests, nginx version, pkg-oss ref)
TRIAGE.md                 # which CVEs were chosen and why
NOTES.md                  # decisions and the things that broke along the way
```

## What broke, and what I learned

`NOTES.md` is the running log. The ones worth calling out:

- A `set -e` trap: a failed `docker pull` inside a command substitution didn't stop
  the script, hiding the real error behind a later one.
- nginx's own packaging tries to download a changelog helper from a dead URL;
  worked around by pre-seeding the changelog.
- **The compat test earned its keep:** the backport applied cleanly and compiled,
  but the first build trusted `dpkg` to apply the quilt series and it silently
  didn't — the image shipped *unpatched*. Only the behavioural test caught it.
  "The patch applies cleanly" is not "the patch is in the binary."
- Carrying the prebuilt modules over needed their runtime libraries too, or they
  failed to `dlopen`.

## Use of AI

I built this with an AI assistant (Claude) and treated it as a fast pair, not an
oracle. It did most of the scaffolding — the scripts, the Dockerfile and
Containerfile, the test harness, the triage/diff tools — from my direction, and
helped research the CVEs and nginx's packaging.

Where it helped: speed, and generating the compatibility suite that then caught a
real bug. Where it was wrong, and I had to catch it: it introduced the `set -e`
bug above; it first asserted the CVE fix would return HTTP 500 when the real
patched behaviour is an empty 200 plus a log line; and at one point it claimed it
had updated a file when it hadn't. I verified every claim against the actual build
and scan output rather than taking its word — which is also how the
patch-not-in-the-binary problem surfaced.
